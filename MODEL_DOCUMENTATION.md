# Model documentation

A model card for the fraud scoring system in this repository. The README explains
what was built and why; this document states what the model is, what it was
trained on, how it was validated, where it fails, and what has to be true for it
to be safe to use.

Everything below is produced by `scripts/run_pipeline.py` at 300,000 transactions
with `seed=42`. Numbers are quoted from `outputs/RESULTS.md` and
`outputs/metrics.json`, which the pipeline generates.

---

## 1. Summary

| | |
|---|---|
| **Model name** | `lightgbm-seed42-300000rows` |
| **Version** | 1.0.0 |
| **Task** | Binary classification of card-not-present transactions, plus a three-way approve/review/decline decision rule |
| **Algorithm** | LightGBM gradient-boosted trees (binary objective), 46 features, native categorical handling |
| **Calibration** | Isotonic regression, fitted on the validation window; monotone, so ranking is preserved |
| **Decision rule** | Two thresholds fitted by exact global cost minimisation under a queue-capacity constraint |
| **Training data** | 210,000 simulated transactions (2018-01-01 to 2018-05-08 UTC) |
| **Primary metric** | PR-AUC (average precision) on the out-of-time window |
| **OOT PR-AUC** | 0.5782 (95% bootstrap CI 0.5002 - 0.6638) against a 0.4111% base rate |
| **OOT ROC-AUC / KS** | 0.9511 / 0.8887 |
| **OOT recall @ 1% capacity** | 88.6% |
| **Serving** | FastAPI, `POST /score`, `POST /score/batch`; serialised bundle via joblib |

## 2. Intended use

### In scope

Scoring individual card-not-present authorisation requests to produce a fraud
probability, a decision, and the drivers behind it, for an issuer or acquirer
with a manual review queue. The system is designed to be operated with a capacity
constraint: the review band is explicitly capped at the share of volume the team
can work.

### Out of scope

* **Any decision affecting a person without human review of a decline.** The
  friction cost in the model is a proxy for customer harm, not a measurement of
  it, and the model has no concept of the reason for a decline being
  communicable to the customer.
* **Credit underwriting, limit setting, or account closure.** The model scores
  transactions, not people. `card_hist_fraud_rate` and `device_hist_fraud_rate`
  are lagged history, not a creditworthiness assessment.
* **Deployment on a different transaction population without revalidation.**
  Feature definitions are tied to a warehouse schema; a different geography,
  product mix, or identity-data provider invalidates the drift reference bins.
* **Regulatory reporting.** No fairness testing across protected groups has been
  performed, because the synthetic data has no such groups.

### Human oversight

The design assumes a human in the loop by construction. The review action exists
precisely because the model's confidence is not treated as sufficient for an
irreversible decision, and every score can be returned with a ranked attribution
and a plain-language narrative. A system operated with the queue switched off
would be a different system with a different risk profile, and the cost model
would have to be refitted with `review_catch_rate = 0`.

## 3. Data

### Provenance

Synthetic, generated by `src/frauddetect/data.py` from
`seed=42`. The IEEE-CIS schema is used so that the real competition extract can
be substituted with `--data-mode real`; the warehouse, encoder, models and
evaluation are shared between the two paths.

The simulator is documented rather than assumed. `outputs/generator_manifest.json`
records every mechanism and its parameters, and the properties the rest of the
pipeline depends on are asserted in the test suite.

### Structure injected

| mechanism | why it is there |
|---|---|
| Account-takeover episodes | fraud arrives in short bursts on one card, not as isolated events |
| Card-testing then escalation | small probes precede the large attempt |
| Repeat victimisation | an attacked card is more likely to be attacked again |
| Shared, rotating device rings | device features carry signal, and the signal moves over time |
| Legitimate spending sprees | the hard negatives; without these the task is merely imbalanced |
| Rising fraud pressure and amount inflation | makes the OOT window genuinely different from train |
| Identity-table coverage below 100% | missingness is itself informative and must not be blanket-imputed |
| Post-hoc chargeback fields | present in the data and forbidden to the model |

### Splits

Chronological. The split is assigned by timestamp rank, not by row order, so a
randomised file cannot silently scramble the boundary.

| window | rows | frauds | rate | period |
|---|---|---|---|---|
| train | 210,000 | 711 | 0.339% | 2018-01-01 to 2018-05-08 |
| validation (test) | 45,000 | 154 | 0.342% | 2018-05-08 to 2018-06-04 |
| out-of-time | 45,001 | 185 | 0.411% | 2018-06-04 to 2018-07-03 |
| **total** | **300,001** | **1,050** | **0.350%** | |

The out-of-time window has a **21% higher fraud rate** than training. That is
intentional: a static threshold that looks fine in-sample will under-flag in
production, and the drift monitor is supposed to catch it.

### Data quality

22 assertions run as part of the warehouse build and are written to a
`data_quality` table rather than printed, so they are auditable after the fact.
The pipeline fails if any is `FAIL`. Highlights as built:

| check | value | status |
|---|---|---|
| rows retained after staging | 300,001 (100.0%) | PASS |
| duplicate transaction ids | 0 | PASS |
| non-positive amounts | 0 | PASS |
| orphan identity rows | 0 | PASS |
| `card2` missing share | 9.31% | INFO |
| `dist1` missing share | 34.79% | INFO |
| identity coverage, fraudulent | 39.05% | INFO |
| identity coverage, legitimate | 22.30% | INFO |

The last two rows are why missingness is a feature: a fraudulent transaction is
**1.75× more likely** to have an identity record at all. Imputing that away would
delete signal.

## 4. Features

46 features: 32 numeric, 14 categorical. LightGBM consumes the categorical
columns natively; the vocabulary is frozen at fit time and unseen levels collapse
to `__rare__`, with absent columns becoming `NaN` (missing), never `0`.

### Groups

| group | count | members | note |
|---|---|---|---|
| Card velocity | 8 | `card_txn_seq`, `card_txn_count_past`, `card_hours_since_prev`, `card_txn_1h`, `card_txn_24h`, `card_amt_sum_24h`, `card_amt_zscore_past`, `card_amt_vs_1h_mean` | strictly backward `RANGE` frames |
| Entity activity | 4 | `addr_txn_count_past`, `email_txn_count_past`, `device_txn_count_past`, `card_distinct_addr_past` | NULL when the entity is unknown |
| Device fan-out | 3 | `device_distinct_card_past`, `device_hist_fraud_rate`, `device_risk_code` | cards sharing one device; detects rings |
| Lagged label history | 3 | `card_hist_fraud_rate`, `card_hist_txn_count`, `addr_hist_fraud_rate` | 60-day resolution lag applied |
| Amount and timing | 7 | `TransactionAmt`, `TransactionAmt_log`, `dist1_log`, `hour_of_day`, `day_of_week`, `days_since_first_seen`, `is_night` | |
| Coverage and mismatch | 6 | `identity_missing`, `card2_missing`, `card5_missing`, `addr1_missing`, `dist1_missing`, `mismatch_count` | missingness is signal, not noise |
| Frequency encoding | 1 | `card1_freq_code` | fitted on the training window only |
| Categoricals | 14 | `ProductCD`, `card4`, `card6`, `P_emaildomain_bucket`, `R_emaildomain_bucket`, `DeviceType`, `M1`-`M6`, `id_31_browser`, `id_33_screen` | native LightGBM categorical splits |

### The two causal rules

Every window frame ends **before** the current row, and a label may only be used
once it has **resolved** — 60 days after the transaction, the simulator's
chargeback settlement horizon. Both are enforced in SQL and re-checked in Python
against an independent computation.

### Forbidden features

`is_fraud` (the target), `chargeback_amount`, `chargeback_days`, `case_closed`
(known only after settlement), and `C1`-`C6` (vendor counters that include later
transactions or an all-time mean). `TransactionID` is a row key; `card1`, `addr1`
and `TransactionDT` are replaced by derived quantities.

They remain in the mart for audit and are classified in a `feature_governance`
view. `assert_no_forbidden_features` fails the pipeline if any reaches the design
matrix.

## 5. Training

```
objective          binary
features           46 (32 numeric, 14 categorical, native categorical splits)
class balance      0.339% positive - handled by the objective and the evaluation,
                   not by resampling (see below)
early stopping     none; the validation window is reserved for calibration and
                   threshold selection, so it cannot also be used to stop the fit
seed               42
```

**Resampling is deliberately not used in the production model.** The study in
section 7 of the README shows that SMOTE-ENN is worth about +0.047 PR-AUC under
an honest protocol, which is real but small, and that most of the apparent gain
in the literature comes from applying the sampler before the split. The shipped
model is the unweighted baseline (OOT PR-AUC 0.6044) so that the reported numbers
do not depend on a sampler's hyperparameters. The comparison is kept in the
pipeline as a measured result rather than adopted as a default.

A caution recorded from the same study: `class_weight='balanced'` scores
**0.1123** with a ROC-AUC of **0.5647**, barely above chance. That is not a
subtle degradation and it is not visible in ROC-AUC.

### Calibration

Isotonic regression fitted on the validation window and applied to the out-of-time
window.

| | ECE |
|---|---|
| raw LightGBM probability | 0.00232 |
| after isotonic calibration | **0.00090** |

Calibration is not cosmetic here. The optimal decision threshold is a function of
the predicted probability, so an uncalibrated score produces a threshold that is
wrong by the same factor. The concrete consequence is in the README: a fixed 0.5
threshold on the raw score captures 31% of fraud and loses 2.7× more than the
fitted rule.

## 6. Evaluation

### Protocol

Thresholds and the calibrator are fitted on the **validation** window and frozen.
The **out-of-time** window is used for evaluation only; nothing that fits
anything touches it.

### Discrimination

| model | test PR-AUC | OOT PR-AUC | OOT ROC-AUC | OOT KS |
|---|---|---|---|---|
| **LightGBM** | 0.4614 | **0.6044** | 0.9500 | 0.8927 |
| Logistic regression | 0.4427 | 0.5879 | 0.9500 | 0.8813 |
| Isolation forest | 0.1458 | 0.2221 | 0.9567 | 0.8694 |
| Autoencoder | 0.1047 | 0.1838 | 0.9579 | 0.8484 |

Both unsupervised detectors beat both supervised models on ROC-AUC and lose to
them by 2-3× on PR-AUC. At a 0.35% base rate that is expected, and it is the
reason accuracy and ROC-AUC are not reported as headline numbers. An all-negative
classifier is 99.59% accurate.

### Capacity-constrained recall

This is the operationally meaningful metric: how much fraud sits inside the top
slice of the score distribution.

| capacity | recall | precision | lift |
|---|---|---|---|
| 0.1% | 15.1% | 62.2% | 151.3× |
| 0.2% | 34.1% | 70.0% | 170.3× |
| 0.5% | **76.8%** | 63.1% | 153.5× |
| 1% | **88.6%** | 36.4% | 88.7× |
| 2% | 90.3% | 18.6% | 45.1× |
| 5% | 90.3% | 7.4% | 18.1× |

Two readings. Precision **peaks at 0.2%** and falls monotonically after it, so
expanding a queue past that point dilutes it. And recall is 76.8% at 0.5% but
only 88.6% at 1% — the useful information is concentrated in a very small head,
which is what makes a tight queue viable and a loose one wasteful.

### Uncertainty

The OOT window contains 185 frauds. Point estimates on so few positives are noisy,
so a bootstrap interval is reported alongside every PR-AUC: **0.5002 - 0.6638**.
Any comparison between two models closer than about 0.05 on this window is not
resolvable with this data.

### Segment behaviour

Fraud rate on the out-of-time window, bucketed by the card's **resolution-lagged**
resolved fraud rate. The 60-day lag means a transaction cannot contribute to the
bucket it is counted in.

| bucket | n | share of volume | fraud rate | vs no-history |
|---|---|---|---|---|
| no resolved card history | 39,472 | 87.7% | 0.030% | 1.0× |
| resolved history, 0% fraud | 3,257 | 7.2% | 0.123% | 4.0× |
| resolved history, 0-1% | 427 | 0.9% | 0.234% | 7.7× |
| resolved history, 1-5% | 1,813 | 4.0% | **9.266%** | **305×** |
| resolved history, 5-15% | 12 | 0.03% | 0% | — |

**4.0% of the volume carries 90.8% of the fraud** (168 of 185 cases).
`card_hist_fraud_rate` is the single strongest feature in the model, and it is
strong for a structural reason: a card that has already been taken over once is
markedly more likely to be hit again.

Two honest caveats. First, this concentration is a **property of the simulator**,
where repeat victimisation was built in deliberately; a real population that
lacks that mechanism would lean on the feature far less, and reported performance
would be lower. The lagged-history features should be treated as the mechanism
the model exploits rather than as a forecast of real-world performance. Second,
the 5-15% bucket has 12 rows and a 0% rate, which is noise and is shown as such
rather than smoothed away.

## 7. Decision policy

### Cost model

| parameter | value | basis |
|---|---|---|
| `fraud_loss_ratio` | 1.00 | an approved fraud loses the full amount |
| `review_cost` | 8.00 | analyst time per alert |
| `decline_friction_cost` | 25.00 | goodwill burnt on an innocent customer |
| `min_review_amount` | 5.00 | below this an analyst costs more than the exposure |
| `review_catch_rate` | 0.70 | share of reviewed fraud stopped before settlement |
| `max_review_rate` | 0.02 | share of volume the queue can work per day |

**These are assumptions, not measurements.** They are stated as named constants
with documented rationale in `config.py` and are the first thing to replace with
an institution's own numbers. The optimum is most sensitive to
`decline_friction_cost` and `review_catch_rate`.

### Result

Applied unchanged to the out-of-time window:

| policy | cost | cost/10k | review % | decline % | fraud captured |
|---|---|---|---|---|---|
| approve everything | 20,387 | 4,530 | — | — | 0% |
| fixed 0.5 threshold | 14,994 | 3,332 | 0% | 0.18% | 31.4% |
| **fitted policy (frozen)** | **5,561** | **1,236** | **0%** | **0.62%** | **84.3%** |

The fitted policy has **two** actions rather than three: the review band is
empty. See section 7.1.

### 7.1 Why the review band is empty

The three-way rule is implemented and its optimum is global. On this book that
optimum is approve-or-decline.

The mechanism is the granularity of the decision boundary. A threshold rule can
only express `score >= t`, so a band can only be drawn between two *distinct*
score values. Isotonic calibration maps an interval of raw scores onto one
probability, so the flagged tail becomes a handful of wide tiers; at this base
rate a band therefore has to be a whole tier, which means paying $8 to inspect a
mixed block of alerts to stop a few frauds. The arithmetic does not close.

This is **not** an artefact of the calibration choice. Repeating the fit with a
Platt-scaled score and with the raw uncalibrated score — both of which have
45,000 distinct values and no ties at all — produces the same empty band.

### 7.2 What the queue would have to cost

Rather than adjust the cost model until a band appeared, the pipeline sweeps the
price of an alert and the catch rate and reports where the answer flips
(`outputs/tables/23_review_band_sensitivity.csv`).

| alert cost | catch 30% | catch 50% | catch 70% | catch 90% |
|---|---|---|---|---|
| 1 | 0 | +22 | +308 | +2,078 |
| 2 | 0 | 0 | +176 | +1,785 |
| 4 | 0 | 0 | +3 | +1,327 |
| **8** *(shipped)* | 0 | 0 | **0** | +537 |
| 16 | 0 | 0 | 0 | 0 |

Figures are the saving of the three-way optimum over the two-way optimum on the
validation window.

At the configured 70% catch rate the band pays for itself only while an alert
costs about **4 or less**. Two operational conclusions:

* **The catch rate matters more than the price.** Moving the catch rate from 70%
  to 90% at the *unchanged* $8 is worth more than cutting the alert price from $8
  to $1. A review that only stops part of what it finds has already lost most of
  the money by the time an analyst reaches it.
* The break-even is a number, so "should we fund a review queue?" is answerable
  from the model rather than from opinion.

### Guarantees

* The thresholds are the **global** optimum under the stated cost model, not a
  grid-search best. Verified against exhaustive enumeration in the test suite.
* Cuts are only ever taken between **distinct** score values, so the reported
  cost equals the cost of actually applying the policy. This matters because
  isotonic calibration creates wide ties; an optimiser that ignored them would
  report a saving no threshold can deliver.
* The capacity cap is enforced on **transactions**, not on score tiers.

### Known weakness

**There is no review band at the shipped cost model** (section 7.1). A
deployment that needs one has three options, in increasing order of honesty:
lower the alert price below the break-even, raise the fraction of reviewed fraud
actually stopped, or refit the model to produce a finer gradient in the flagged
tail — isotonic calibration is partly responsible for the coarse tiers.

Note also that the sweep is over a **single validation window**. The break-even is
a point estimate on 154 positives and should be read as an order of magnitude
rather than a price list.

## 8. Explanation

Every score can be returned with:

* the **calibrated probability** and the raw margin;
* the **decision** implied by the frozen thresholds;
* the **top SHAP contributions** for that transaction, from LightGBM's
  `pred_contrib=True`, computed on the raw margin so the contributions add up to
  the log-odds and can be checked arithmetically;
* a **narrative** sentence naming the drivers, with absent history rendered as
  `missing` rather than `nan`.

Exactness is cross-validated: the test suite asserts that LightGBM's
`pred_contrib` and `shap.TreeExplainer` agree to numerical tolerance. Two
independent implementations of the same algorithm producing the same numbers is
the strongest evidence available that the attribution is correct.

Permutation importance is computed by shuffling the **DataFrame column**, so
categorical splits survive; a conversion to `ndarray` would permute integer codes
and describe a different model.

## 9. Fairness and ethics

**Not assessed.** The synthetic data has no protected attributes, no real
customers, and no proxies for them, so a fairness audit would be theatre.

For a real deployment, the following would have to be done before use and are
not covered here:

* segment performance by protected group and by geography, on both discrimination
  and the **decision** (the friction cost is borne unevenly if false declines
  concentrate);
* an adverse-action reason that a human can communicate, derived from the SHAP
  attribution and reviewed for legibility;
* confirmation that `card_hist_fraud_rate` and `device_hist_fraud_rate` do not
  encode a proxy for a protected characteristic through the identity-data
  coverage channel;
* a documented appeal path for declined customers.

## 10. Monitoring

| signal | reference | action |
|---|---|---|
| Score PSI | frozen bins at fit time | observe ≥ 0.10, retrain ≥ 0.25 |
| Score KS | validation window | investigate a large shift in either direction |
| Feature PSI, top 15 | frozen bins | per-feature review |
| Monthly stability | first month of OOT | label-rate and score drift together |
| Calibration | rolling ECE | refit the calibrator if ECE degrades |

As built, the OOT window reports **PSI 10.5737, KS 0.9315, verdict `retrain`**,
with the mean score nearly doubling. That is the correct verdict rather than a
malfunction: the window is six months after training and fraud pressure rises
over it by construction. A monitor that stayed quiet would be the broken one.

The reference bins are derived once at fit time and frozen. Recomputing them from
each incoming window would make every distribution look stable by definition,
which is the most common way a drift monitor is quietly disabled.

## 11. Limitations

1. **Simulated data.** Structured to contain what the methods exploit, with every
   mechanism recorded in `generator_manifest.json`, but not real. Absolute
   performance numbers do not transfer; the methodology does.
2. **Single OOT window, 185 frauds.** The bootstrap interval is wide. Differences
   below roughly 0.05 PR-AUC are not resolvable.
3. **Cost model is assumed.** See section 7. The optimum is sensitive to the
   friction term in particular.
4. **`max_review_rate` is a guardrail, not a measured capacity.** Real queue
   capacity varies by hour and day; a single scalar flattens that.
5. **60-day label lag is a simulator constant.** If real chargebacks settle
   faster or slower, the lagged-history features shift in strength.
6. **Serving takes engineered features, not raw transactions.** Point-in-time
   correctness is the caller's responsibility; the service documents this rather
   than pretending to recompute history from one request.
7. **No fairness assessment.** See section 9.

## 12. Reproducibility

```bash
python -m pip install -r requirements.txt
python scripts/run_pipeline.py --transactions 300000 --seed 42
```

Deterministic for a fixed `--transactions` and `--seed`. Produces
`outputs/metrics.json` (every number in this document),
`outputs/RESULTS.md`, 17 figures, 21 CSV tables, and
`outputs/model/scoring_bundle.joblib` — the encoder, model, calibrator and frozen
thresholds versioned together, so a served score is reproducible from the artifact
alone.

The bundle records its own provenance:

```json
{
  "version": "lightgbm-seed42-300000rows",
  "trained_on": "210000 transactions",
  "metrics": {
    "oot_pr_auc": 0.5782,
    "oot_roc_auc": 0.9511,
    "oot_recall_at_1pct": 0.8865
  },
  "cost_model": {
    "fraud_loss_ratio": 1.0,
    "review_cost": 8.0,
    "decline_friction_cost": 25.0,
    "min_review_amount": 5.0,
    "review_catch_rate": 0.7,
    "max_review_rate": 0.02
  },
  "transactions_realised": 300001
}
```

`version` is keyed to the **requested** transaction count, not the realised row
count. Episodes add transactions on top of the base stream, so a
`--transactions 300000` run produces 300,001 rows; a version string that
disagreed with the command that produced it would be worse than useless during an
incident review. The realised count is carried separately.
